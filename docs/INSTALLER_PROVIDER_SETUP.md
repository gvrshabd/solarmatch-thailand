# Installer providers: prelaunch setup and verification

All adapters are server modules under `lib/installer/providers`. Their default mode must be `off`. The caller controls environment configuration, database persistence, tenant authorization, loopback-only access to local fixtures, idempotent ledger issuance and the durable notification outbox. No production calls or messages were made during implementation. Never print configuration objects, raw webhook bodies, phone numbers, codes or bearer links in logs.

## Payment: Omise provider-hosted components

Use `createHostedOrder(order, config)` after persisting an order with immutable company, package, amount and currency. In sandbox it returns `checkout` for OmiseCard, not a successful payment. The browser loads `https://cdn.omise.co/omise.js`, configures the returned public test key and calls `OmiseCard.open`. The token/source callback submits only its identifier and the application's order ID to the authenticated server. Raw card details never enter SolarMatch.

The server calls `createCharge(persistedOrder, tokenOrSourceId, config)`. Persist the returned `payment.chargeId` as the order's authoritative provider ID before applying payment state. Open `authorizationUrl` when supplied; display `qrImageUrl` for PromptPay when supplied. A redirect, a displayed QR and charge authorization alone must never issue credits. `paid` requires successful paid/captured charge confirmation. Payment capture remains separate from credit issuance, earned enquiry fees and bank settlement.

Configuration contract: `mode: 'off' | 'local-test' | 'sandbox'`, `sandboxEnabled`, `secretKey`, `publicKey`, `webhookSecret`, `activatedMethods`, `activatedCardBrands`. Sandbox requires `skey_test_...` and `pkey_test_...`; live keys are rejected even when flags are enabled. Accepted method identifiers are `credit_card`, `promptpay`, `mobile_banking_bbl`, `mobile_banking_kbank`, `mobile_banking_ktb`, `mobile_banking_bay`, `mobile_banking_scb`, `truemoney_jumpapp`. Only configured, merchant-activated methods may be shown. Configure card brands separately (`Visa`, `MasterCard`). Token card brand and source type/amount/currency are checked before charge creation.

Persisted settings expose `paymentMethods` and `paymentCardBrands`, both defaulting to empty arrays. Disabling purchases prevents new checkout/charge creation; test-key-only read verification still reconciles already-created orders. Orders reserve one outbound authorization attempt atomically and retain a `reconciliation-required` state after ambiguous failures; they are never automatically recreated. Ledger issuance offsets any existing reversal debt first. Refunds/reversals claw available credit before recording remaining spent value as debt. Cumulative partial refunds remove proportional whole credit units rounded upward; confirm that draft rounding policy before launch. Late/replayed paid or lower-refund events cannot resurrect reversed credit or downgrade a full reversal.

`verifyPaymentEvent(rawBody, headers, config)` verifies timestamped raw-body HMAC if a sandbox webhook secret is configured. Omise secrets are Base64 decoded; the signed string is `<timestamp>.<raw body>`, compared as hex, with a five-minute replay window and rotation signatures supported. Independently retrieve the event using the authenticated Events API regardless of signature configuration; embedded browser/webhook values are not financial authority. `confirmPayment({orderId,providerOrderId,amountMinor,currency},chargeId,config)` then independently retrieves the charge and checks persisted charge ID, `metadata.solarmatch_order_id`, integer amount, THB currency and test mode. Replay of a verified event still requires a unique database event/ledger key. Refund/reversal amounts are returned for reconciliation; no refunds are initiated by these adapters.

Local checkout is explicitly synthetic (`checkout: null`, provider `local-test`). Local event fixtures require a separate `localEventSecret` and the same timestamp HMAC. Root code may synthesize a fixture charge after loopback validation and use `normalizePayment`; it must never use that helper as a substitute for authenticated provider confirmation in sandbox. Missing credentials do not select local mode automatically.

Current official documentation: [Omise.js prebuilt form and supported methods](https://docs.omise.co/omise-js), [Charges API](https://docs.omise.co/charges-api), [webhook signatures and independent verification](https://docs.omise.co/api-webhooks), [merchant/test account requirements](https://docs.omise.co/thailand). Reviewed 11 October 2026. The former `/links` documentation is no longer available; [current Payment Links+ API](https://docs.omise.co/payment-links-apis) uses separate credentials without a documented test-key discriminator. This implementation therefore uses the current hosted components instead of assuming Payment Links+ is safe for sandbox collection.

Still required: merchant test account, activated test methods, public/secret test keys, test webhook secret and configured callback URL. Exercise each activated method, asynchronous completion, 3DS/mobile redirect, expired/failed payments, duplicate events, missing browser return, refund/reversal reconciliation and charge-create timeout recovery with provider credentials. Charge creation is not assumed idempotent: lock the persisted order attempt, and reconcile ambiguous timeouts before permitting another creation attempt. Poll Events/Charges for missed events; current Omise docs do not guarantee webhook retries.

## SMS: Twilio Messages test credentials

`sendMessage({to,body,idempotencyKey}, config)` validates E.164 recipients and captures the exact payload in `local-test`; caller persists that capture in the test-message table. Do not log it. The SMS body may contain a local OTP, so previews require the same local-only protection as the challenge endpoint.

Sandbox requires `outboundEnabled`, `credentialsAreTest`, `accountSid` and `authToken`; it uses the documented Twilio magic sender `+15005550006`. Supply legacy Twilio **test credentials**, never trial/live account credentials. These credentials simulate Messages API operations without contacting phone numbers. Twilio's current docs state that new-console users cannot create those legacy test credentials, so local captures remain the default if they are unavailable. No live SMS mode exists here. The caller owns resend cooldown, hashing, expiry, attempt limits and abuse limits.

Twilio Messages does not provide the application's ledger/outbox idempotency guarantee: `idempotencyKey` identifies the local outbox record; use a database claim/lease and reconcile ambiguous responses. Test credential calls do not trigger status callbacks and cannot verify actual Thai deliverability. Provider acceptance must never mean homeowner receipt or OTP verification.

Sources: [Twilio test credentials and magic numbers](https://www.twilio.com/docs/iam/test-credentials), [Messaging API](https://www.twilio.com/docs/messaging/api). Still required for future live operation: select an approved Thai-capable sender/provider, verify costs/deliverability and sender requirements, and implement a separately reviewed live-mode path. Do not enable it as part of this task.

## LINE Official Account / Messaging API

`verifyLineWebhook(rawBody, headers, config)` requires `channelSecret`, checks `X-Line-Signature` as Base64 HMAC-SHA256 over the unmodified UTF-8 body, then returns events. Persist `webhookEventId` under a unique constraint before side effects. Account-linking destinations come only from signed source user IDs; a typed display name/LINE ID is not a destination. Treat event IDs as replay keys, and `deliveryContext.isRedelivery` as informational.

Secure sequence: obtain the LINE user ID through a signed webhook; call `requestLinkToken(userId, config)`; show the installer a login/approval-protected linking page; create at least 128 random bits of nonce, store its hash bound to the company/session with short expiry and one-time consumption; redirect with `lineAccountLinkUrl(linkToken,nonce)`. Only a signed `accountLink` event with `link.result === 'ok'`, the expected user ID and the matching unconsumed nonce confirms association. Link tokens are one-use and valid for ten minutes. Support unlinking. Never allow a bearer-link visitor to alter LINE settings.

`sendEnquiryNotification` accepts only enquiry reference, product, credits/trial label and enquiry URL. Thai is the default, with English supported. Homeowner name, phone and assessment are not accepted in this input contract. Prefer the authenticated per-delivery page URL (no token query, no fragment). Notification acceptance is distinct from availability in the portal and from viewing. Persist one UUID `retryKey` per outbox record and reuse it. The adapter recognizes LINE's accepted-request 409 retry response; retries never create another delivery/charge.

Config: `mode`, `channelSecret`, `accessToken`, `outboundEnabled`, `sandboxRecipients`. LINE has no SMS-like test transport: sandbox outbound API calls can send real messages, so both an explicit outbound gate and a test-recipient allowlist are required, and those flags remain off during this task. Local mode returns captured payloads and creates clearly synthetic link tokens without external requests. No LINE Notify API is used.

The `LINE_TEST_RECIPIENTS` runtime setting is a JSON array of allowed test user IDs. A signed `follow` or a text message `LINK` creates a short-lived opaque invitation and sends/captures an installer login URL. Invitations are hash-stored and limited to three per LINE recipient per ten minutes. The portal removes `linkRequest` from the visible URL immediately, retains it in memory, and submits it only through an authenticated approved company owner's action. A one-time invitation claim creates the nonce challenge; a signed successful account-link event confirms the association. Invitation notification retries derive the same token and retry UUID with separate HMAC domains, so the database need not store the raw invitation token. Secret rotation may invalidate an uncompleted invitation; issue a new `LINK` request.

Sources: [account linking and ownership checks](https://developers.line.biz/en/docs/messaging-api/linking-accounts/), [webhook signature verification](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/), [webhook redelivery](https://developers.line.biz/en/docs/messaging-api/receiving-messages/), [retry keys](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/), [Messaging API reference](https://developers.line.biz/en/reference/messaging-api/). Still required: approved OA/channel, secret/access token, configured HTTPS webhook and later explicitly authorized test-recipient exercises. No actual LINE delivery has been verified.

## Checks exercised

`tests/unit/installer-providers.test.ts` exercises nine credential-free fixture tests: disabled/live-key rejection without network calls, authoritative amount/order checks, forged embedded event data, HMAC body tampering/replay, disallowed source amounts, immutable successful source authorization, rejection of undeclared card brands, LINE raw signature verification and outbound/local-capture isolation. These fixtures validate application boundaries; they do not prove provider account configuration, card/payment method activation, SMS deliverability, LINE delivery, settlement or tax invoice compliance.

`tests/unit/installer-payments.test.ts` adds five tests against the complete real SQLite migration chain: repeated/reordered credit issuance, reversal debt and future debt offset, cumulative partial refunds, signed nonce/user matching, and one-time invitation claims. `tests/unit/installer-tenant-share.test.ts` adds seven tests using the shared synthetic D1 adapter: cross-company payment/claim/share rejection, membership scoping, repeated share reads/rotation without billing or deadline renewal, expiry/revocation on withdrawal, assessment-field projection, and duplicate review retaining the original recipient cap. `tests/unit/installer-rate-limit.test.ts` adds two tests for atomic authenticated-user throttling and rejecting untrusted IP headers. These 23 tests passed locally; no provider sandbox credentials or real external acceptance/delivery have been exercised.

Installer mutations are limited to 30 per minute per authenticated user; account-free share reads are limited to 60 per minute per trusted Cloudflare client address. Rate-limit keys use a separate HMAC domain and require the configured installer signing secret. Arbitrary browser IP headers are ignored without Cloudflare request metadata. If a server adapter strips `Request.cf`, unauthenticated share reads use a common fail-closed bucket: validate edge metadata propagation before launch. Admin controls remain separately protected and are not subject to customer throttling.

Duplicate review never resets the slots of the same property's canonical enquiry. Migration `0009_installer_verification_evidence.sql` adds durable `leads.phone_verified_at` evidence, which distinct-project review uses even after expired OTP challenges are cleaned up. Legacy requests remain unverified; the durable timestamp is written only through successful verification or explicit synthetic fixtures. Review still requires the separately verified new submission and a genuinely different canonical property key. A positive retention period must be explicitly configured for the admin preview; preview does not purge any data or establish final policy.

Background jobs validate their environment before touching the database: local-test requires an explicitly configured loopback `INSTALLER_BASE_URL`; sandbox requires an HTTPS URL with a non-loopback hostname. Supply an origin URL without credentials, path, query or fragment. Disabled jobs remain inert. This prevents a remote worker from using local fixture mode merely because the mode flag was misconfigured.

`tests/unit/installer-jobs-environment.test.ts` verifies 13 environment cases, including rejection before database access. `tests/unit/installer-outbox-integration.test.ts` verifies three complete SQLite service flows: delivery through durable outbox and captured LINE/homeowner SMS, repeat execution without another charge, suppression cancelling pending messages and revoking sharing, and overnight release at 09:00 Bangkok without extending the request timestamp. The integration tests reject every network request. These tests passed locally, with TypeScript and focused lint checks; they are synthetic transport evidence, not provider acceptance or delivery evidence.

LINE invitation creation now enforces its three-per-ten-minute recipient limit within the insertion statement. A concurrent eight-event test confirms that only three invitations and three local notification captures are created. Same-event retries retain the original token, expiry and provider retry key; one-time claims and account-link nonce consumption remain atomic.
