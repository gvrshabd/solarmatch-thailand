# Installer providers: prelaunch setup and verification

All adapters are server modules under `lib/installer/providers`. Their default mode must be `off`. The caller controls environment configuration, database persistence, tenant authorization, loopback-only access to local fixtures, idempotent ledger issuance and the durable notification outbox. No production calls or messages were made during implementation. Never print configuration objects, raw webhook bodies, phone numbers, codes or bearer links in logs.

## Payment: Omise provider-hosted components

Use `createHostedOrder(order, config)` after persisting an order with immutable company, package, amount and currency. In sandbox it returns `checkout` for OmiseCard, not a successful payment. The browser loads `https://cdn.omise.co/omise.js`, configures the returned public test key and calls `OmiseCard.open`. The token/source callback submits only its identifier and the application's order ID to the authenticated server. Raw card details never enter SolarMatch.

The server calls `createCharge(persistedOrder, tokenOrSourceId, config)`. Persist the returned `payment.chargeId` as the order's authoritative provider ID before applying payment state. Open `authorizationUrl` when supplied; display `qrImageUrl` for PromptPay when supplied. A redirect, a displayed QR and charge authorization alone must never issue credits. `paid` requires successful paid/captured charge confirmation. Payment capture remains separate from credit issuance, earned enquiry fees and bank settlement.

Configuration contract: `OMISE_PROVIDER_MODE=off|sandbox|live` is deliberate and defaults to off. Local platform mode always uses captured payments. Sandbox requires `INSTALLER_PLATFORM_MODE=sandbox`, `OMISE_PROVIDER_MODE=sandbox`, enabled purchases in persisted settings, and matching `skey_test_...`/`pkey_test_...` keys. Live requires `INSTALLER_PLATFORM_MODE=production`, `OMISE_PROVIDER_MODE=live`, `OMISE_LIVE_ENABLED=true`, enabled purchases in persisted settings, and matching `skey_live_...`/`pkey_live_...` keys. A live-looking key by itself never selects live mode. The global pause blocks new orders and authorizations. All live flags and purchase settings remain off. Accepted method identifiers are `credit_card`, `promptpay`, `mobile_banking_bbl`, `mobile_banking_kbank`, `mobile_banking_ktb`, `mobile_banking_bay`, `mobile_banking_scb`, `truemoney_jumpapp`. Only configured, merchant-activated methods may be shown. Configure card brands separately (`Visa`, `MasterCard`). Token card brand and source type/amount/currency are checked before charge creation.

Persisted settings expose `paymentMethods` and `paymentCardBrands`, both defaulting to empty arrays. Disabling purchases prevents new checkout/charge creation; explicitly configured matching test or live keys still permit read-only verification of existing orders. Orders reserve one outbound authorization attempt atomically and retain a `reconciliation-required` state after ambiguous failures; they are never automatically recreated. Ledger issuance offsets any existing reversal debt first. Refunds/reversals claw available credit before recording remaining spent value as debt. Cumulative partial refunds remove proportional whole credit units rounded upward; confirm that draft rounding policy before launch. Late/replayed paid or lower-refund events cannot resurrect reversed credit or downgrade a full reversal.

`verifyPaymentEvent(rawBody, headers, config)` verifies timestamped raw-body HMAC if a sandbox webhook secret is configured; live mode requires one. Omise secrets are Base64 decoded; the signed string is `<timestamp>.<raw body>`, compared as hex, with a five-minute replay window and rotation signatures supported. Independently retrieve the event using the authenticated Events API regardless of signature configuration; embedded browser/webhook values are not financial authority. `confirmPayment({orderId,providerOrderId,amountMinor,currency},chargeId,config)` independently retrieves the charge and checks persisted charge ID, `metadata.solarmatch_order_id`, integer amount, THB currency and matching test/live mode. It remains available for read-only reconciliation after new purchases are disabled. Replay of a verified event still requires a unique database event/ledger key. Refund/reversal amounts are returned for reconciliation; no refunds are initiated by these adapters. An admin-only manual association helper validates a proposed charge against the stored order with Omise before linking it; it never creates a second charge.

Local checkout is explicitly synthetic (`checkout: null`, provider `local-test`). Local event fixtures require a separate `localEventSecret` and the same timestamp HMAC. Root code may synthesize a fixture charge after loopback validation and use `normalizePayment`; it must never use that helper as a substitute for authenticated provider confirmation in sandbox. Missing credentials do not select local mode automatically.

Current official documentation: [Omise.js prebuilt form and supported methods](https://docs.omise.co/omise-js), [Charges API](https://docs.omise.co/charges-api), [webhook signatures and independent verification](https://docs.omise.co/api-webhooks), [merchant/test account requirements](https://docs.omise.co/thailand). Reviewed 11 October 2026. The former `/links` documentation is no longer available; [current Payment Links+ API](https://docs.omise.co/payment-links-apis) uses separate credentials without a documented test-key discriminator. This implementation therefore uses the current hosted components instead of assuming Payment Links+ is safe for sandbox collection.

Still required: merchant test account, activated test methods, public/secret test keys, test webhook secret and configured callback URL. Exercise each activated method, asynchronous completion, 3DS/mobile redirect, expired/failed payments, duplicate events, missing browser return, refund/reversal reconciliation and charge-create timeout recovery with provider credentials. Charge creation is not assumed idempotent: lock the persisted order attempt, and reconcile ambiguous timeouts before permitting another creation attempt. Poll Events/Charges for missed events; current Omise docs do not guarantee webhook retries.

Scheduled `reconcilePendingPayments(db,request)` reads at most 30 known Omise charges per run. It cycles by oldest `last_reconciliation_at`, including already credited orders so delayed refunds and reversals can be found. It runs even when new purchases are disabled, but only with an explicitly selected matching provider mode and secret key; missing configuration yields a skipped summary and no provider request. Each lookup checks charge ID, order metadata, amount, currency and test/live flag before the immutable ledger service applies a change. A failing order records a short error code on that order and does not stop later lookups. Migration `0013_installer_payment_reconciliation.sql` adds the timestamp and error columns. Orders with an ambiguous charge attempt and no saved charge ID are counted in `manualAssociationRequired`; an authorized operator must find the charge in the Omise dashboard and use the separately protected `associateProviderCharge` helper, which retrieves and validates it before linking. This process never creates, refunds or reverses an Omise charge. No scheduled provider read has been exercised with real credentials.

## SMS: Twilio Messages

`sendMessage({to,body,idempotencyKey}, config)` validates E.164 recipients and captures the exact payload in `local-test`; caller persists that capture in the test-message table. Do not log it. The SMS body may contain a local OTP, so previews require the same local-only protection as the challenge endpoint.

Sandbox requires `SMS_PROVIDER_MODE=sandbox`, `OUTBOUND_MESSAGES_ENABLED=true`, `SMS_CREDENTIALS_ARE_TEST=true`, `SMS_ACCOUNT_SID` and `SMS_AUTH_TOKEN`; it uses the documented Twilio magic sender `+15005550006`. Supply legacy Twilio **test credentials**, never trial/live account credentials. These credentials simulate Messages API operations without contacting phone numbers. Twilio's current docs state that new-console users cannot create those legacy test credentials, so local captures remain the default if they are unavailable. Live mode requires `INSTALLER_PLATFORM_MODE=production`, `SMS_PROVIDER_MODE=live`, `SMS_LIVE_ENABLED=true`, `OUTBOUND_MESSAGES_ENABLED=true`, `SMS_CREDENTIALS_ARE_TEST=false`, account credentials and an approved `SMS_MESSAGING_SERVICE_SID` or `SMS_FROM` sender. No flag or sender is active by default. The caller owns one-time challenge hashing, five-minute expiry, one-minute resend cooldown, five verification attempts and abuse limits. Twilio's initial queued/accepted status is provider acceptance, not phone delivery; validate Thai sender registration, account capability, costs and delivery status before launch.

Twilio Messages does not provide the application's ledger/outbox idempotency guarantee: `idempotencyKey` identifies the local outbox record; use a database claim/lease and put ambiguous sends into manual reconciliation instead of blindly retrying. Test credential calls do not trigger status callbacks and cannot verify actual Thai deliverability. Provider acceptance must never mean homeowner receipt or OTP verification.

Sources: [Twilio test credentials and magic numbers](https://www.twilio.com/docs/iam/test-credentials), [Messages resource and sender requirements](https://www.twilio.com/docs/messaging/api/message-resource), [message status callbacks](https://www.twilio.com/docs/messaging/guides/outbound-message-status-in-status-callbacks). A live adapter is coded but no live message or Thai deliverability has been verified. Do not enable it as part of this task.

## Authentication email: Resend

Local mode captures verification and password-reset URLs in the isolated test database. Outside local mode, `AUTH_EMAIL_PROVIDER_MODE=off|sandbox|live` defaults off. Sandbox requires matching platform mode, `OUTBOUND_MESSAGES_ENABLED=true`, verified `AUTH_EMAIL_FROM`, `AUTH_EMAIL_PROVIDER_TOKEN`, and HTTPS `INSTALLER_BASE_URL`. Live additionally requires production platform mode and `AUTH_EMAIL_LIVE_ENABLED=true`. The adapter rejects links with a different origin, passes only in-memory links to Resend, and reports delivery API failures to the authentication caller. It uses an `Idempotency-Key` derived from the specific link; Resend documents a 24-hour idempotency window, so this is not a permanent deduplication record. Do not log recovery URLs or provider error bodies. Verify sending domain ownership and DNS with the provider before activation; no DNS was changed here. Sources: [Resend Send Email API](https://resend.com/docs/api-reference/emails/send-email), [Resend idempotency](https://resend.com/changelog/idempotency-keys). Real inbox delivery and recovery behavior remain untested.

## LINE Official Account / Messaging API

`verifyLineWebhook(rawBody, headers, config)` requires `channelSecret`, checks `X-Line-Signature` as Base64 HMAC-SHA256 over the unmodified UTF-8 body, then returns events. Persist `webhookEventId` under a unique constraint before side effects. Account-linking destinations come only from signed source user IDs; a typed display name/LINE ID is not a destination. Treat event IDs as replay keys, and `deliveryContext.isRedelivery` as informational.

Secure sequence: obtain the LINE user ID through a signed webhook; call `requestLinkToken(userId, config)`; show the installer a login/approval-protected linking page; create at least 128 random bits of nonce, store its hash bound to the company/session with short expiry and one-time consumption; redirect with `lineAccountLinkUrl(linkToken,nonce)`. Only a signed `accountLink` event with `link.result === 'ok'`, the expected user ID and the matching unconsumed nonce confirms association. Link tokens are one-use and valid for ten minutes. Support unlinking. Never allow a bearer-link visitor to alter LINE settings.

`sendEnquiryNotification` accepts only enquiry reference, product, credits/trial label and enquiry URL. Thai is the default, with English supported. Homeowner name, phone and assessment are not accepted in this input contract. Prefer the authenticated per-delivery page URL (no token query, no fragment). Notification acceptance is distinct from availability in the portal and from viewing. Persist one UUID `retryKey` per outbox record and reuse it. The adapter recognizes LINE's accepted-request 409 retry response; retries never create another delivery/charge.

Config: `LINE_PROVIDER_MODE=off|sandbox|live`, `channelSecret`, `accessToken`, `outboundEnabled`, `liveEnabled`, `sandboxRecipients`. Sandbox outbound calls can send real messages, so an explicit outbound gate and test-recipient allowlist are required. Production live additionally requires `INSTALLER_PLATFORM_MODE=production`, `LINE_LIVE_ENABLED=true`, `OUTBOUND_MESSAGES_ENABLED=true`, enabled notifications and a database-confirmed linked recipient for enquiry pushes. Signed follow/LINK events can receive linking invitations; signed unfollow events clear company associations and cancel pending LINE pushes. These flags remain off during this task. Local mode returns captured payloads and synthetic link tokens without external requests. LINE may accept a push even for a blocked recipient, so accepted is never recorded as delivered. Persistent 4xx errors require operator intervention; timeouts and 5xx may retry with the original retry key. No LINE Notify API is used.

The `LINE_TEST_RECIPIENTS` runtime setting is a JSON array of allowed test user IDs. A signed `follow` or a text message `LINK` creates a short-lived opaque invitation and sends/captures an installer login URL. Invitations are hash-stored and limited to three per LINE recipient per ten minutes. The portal removes `linkRequest` from the visible URL immediately, retains it in memory, and submits it only through an authenticated approved company owner's action. A one-time invitation claim creates the nonce challenge; a signed successful account-link event confirms the association. Invitation notification retries derive the same token and retry UUID with separate HMAC domains, so the database need not store the raw invitation token. Secret rotation may invalidate an uncompleted invitation; issue a new `LINK` request.

Sources: [account linking and ownership checks](https://developers.line.biz/en/docs/messaging-api/linking-accounts/), [webhook signature verification](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/), [webhook redelivery](https://developers.line.biz/en/docs/messaging-api/receiving-messages/), [retry keys](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/), [Messaging API reference](https://developers.line.biz/en/reference/messaging-api/). Still required: approved OA/channel, secret/access token, configured HTTPS webhook and later explicitly authorized test-recipient exercises. No actual LINE delivery has been verified.

## Checks exercised

The autonomous preparation made no real provider calls. Current Thai sender/URL rules and new-console trial-template limits were rechecked; the actual account/free coverage and owner-controlled recipient were not verified, so only captures are used. LINE browser inspection failed twice before account settings could be observed. Merchant registration, domain purchase and a deployed HTTPS sandbox endpoint remain deferred. Exact later dashboard/callback/secret-name steps and dated primary sources are in `installer-provider-domain-research.txt`. No callback was set to localhost or undeployed production.

`tests/unit/installer-providers.test.ts` exercises credential-free fixtures for disabled/live-key rejection without network calls, authoritative amount/order checks, forged embedded event data, HMAC body tampering/replay, disallowed source amounts, declared card brands, explicit SMS/email/LINE live gates, LINE raw signature verification and local-capture isolation. These fixtures validate application boundaries; they do not prove provider account configuration, card/payment method activation, SMS deliverability, LINE delivery, settlement or tax invoice compliance.

`tests/unit/installer-payments.test.ts` covers repeated/reordered credit issuance, reversal debt and future debt offset, cumulative partial refunds, provider/package mismatch rejection, atomic invitation throttling, signed nonce/user matching, one-time invitation claims and unfollow handling. `tests/unit/installer-payment-reconciliation.test.ts` covers bounded polling, per-order failure continuation, disabled-key skipping and manual charge association. Tenant/share and rate-limit tests use synthetic D1 adapters for company scoping, lifetime recipient limits and trusted request metadata. Final whole-suite totals are recorded in the implementation report after regression; no provider sandbox credentials or real external acceptance/delivery have been exercised.

Installer mutations are limited to 30 per minute per authenticated user; account-free share reads are limited to 60 per minute per trusted Cloudflare client address. Rate-limit keys use a separate HMAC domain and require the configured installer signing secret. Arbitrary browser IP headers are ignored without Cloudflare request metadata. If a server adapter strips `Request.cf`, unauthenticated share reads use a common fail-closed bucket: validate edge metadata propagation before launch. Admin controls remain separately protected and are not subject to customer throttling.

Duplicate review never resets the slots of the same property's canonical enquiry. Migration `0009_installer_verification_evidence.sql` adds durable `leads.phone_verified_at` evidence, which distinct-project review uses even after expired OTP challenges are cleaned up. Legacy requests remain unverified; the durable timestamp is written only through successful verification or explicit synthetic fixtures. Review still requires the separately verified new submission and a genuinely different canonical property key. A positive retention period must be explicitly configured for the admin preview; preview does not purge any data or establish final policy.

Background jobs validate their environment before touching the database: local-test requires an explicitly configured loopback `INSTALLER_BASE_URL`; sandbox and production require HTTPS with a non-loopback hostname. Supply an origin URL without credentials, path, query or fragment. Disabled jobs remain inert. This prevents a remote worker from using local fixture mode merely because the mode flag was misconfigured.

`tests/unit/installer-jobs-environment.test.ts` verifies 13 environment cases, including rejection before database access. `tests/unit/installer-outbox-integration.test.ts` verifies three complete SQLite service flows: delivery through durable outbox and captured LINE/homeowner SMS, repeat execution without another charge, suppression cancelling pending messages and revoking sharing, and overnight release at 09:00 Bangkok without extending the request timestamp. The integration tests reject every network request. These tests passed locally, with TypeScript and focused lint checks; they are synthetic transport evidence, not provider acceptance or delivery evidence.

LINE invitation creation now enforces its three-per-ten-minute recipient limit within the insertion statement. A concurrent eight-event test confirms that only three invitations and three local notification captures are created. Same-event retries retain the original token, expiry and provider retry key; one-time claims and account-link nonce consumption remain atomic.
