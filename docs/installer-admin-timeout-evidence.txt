Originally the later local-access document request hung after the rejected POST.
Repeated combined runs gave 5 pass/1 failure, then 4 pass/2 failures. The failure
was a 30-second document-navigation timeout, not an assertion that auth succeeded.
One local server response completed only after 35,850ms. During the hang,
independent HTTP probes still answered /admin/local-access 200, /admin API 401
and homepage 200 in roughly 140–280ms. Safe browser lifecycle metadata showed
the next GET pending, no response and no page-error event. The rejected 403
produced an expected console-error event; its message text was not exported.

Investigations that did NOT fix it
- Reading the rejected response JSON on the browser side: combined 5/1 and 4/2.
- Cancelling the incoming request body without consuming it: combined 4/2.
- Switching system Chrome 154.0.8037.98 to the Playwright-matched Chromium
  151.0.7922.34: same 4/2 combined result. Browser version alone is not a cause.
- IPv4 loopback was already explicit. Earlier IPv4-only workaround is insufficient.
Experimental worker logging, cancellation-only code and alternate-browser config
were removed. Authentication/origin/CSRF decisions were not changed.

Both desktop and mobile cases timed out on the second document before the fix.
This narrows the trigger to the rejected incoming-body/request lifecycle rather

Retained smallest fix
lib/server/rejected-body.ts discards small unread rejected bodies without parsing,
logging or acting on them. Cleanup is bounded to 32KiB and 100ms; excessive or
stalled streams are cancelled without awaiting potentially stalled cancellation.
lib/server/admin-api.ts invokes it before the SAME 401/403/415 responses.
No successful handler, identity allowlist, JWT/AUD, session rule, CSRF check,
origin rule, content acceptance, database action or test timeout was weakened.
Four unit tests cover small non-JSON input, oversize cancellation, stalled input
with non-settling cancellation, and absent/already-locked bodies.

Complete verification
The original six cases plus both reduced cases passed together (8/8, 9.8s) after
the fix. The original case now also navigates immediately after asserting the
exact 403 error body; its full security and populated controls remain asserted.

run. A later broader run also showed 403 followed by successful GET in 10ms

any unrelated failures and exact commands are in installer-reliability-test-results.txt.
The rejection-body deadline is bounded server cleanup, not increased browser waits.
