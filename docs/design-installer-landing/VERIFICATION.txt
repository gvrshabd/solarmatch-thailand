WEBKIT MOTION INVESTIGATION
The independent requestAnimationFrame probe was also slow, with document.hidden
false. The untouched original prototype reproduces essentially the same slowdown
in the same Windows headless WebKit/device contexts. Over 1.5-second samples:
  scale 1 / 390px: implementation 32 frames, prototype 31
  scale 1 / 1180px: implementation 12 frames, prototype 13
  scale 2 / 390px: implementation 8 frames, prototype 6
  scale 2 / 1180px: implementation 2 frames, prototype 2
  scale 3 / 390px: implementation 2 frames, prototype 2
  scale 3 / 1180px: implementation 1 frame, prototype 2
Raw non-sensitive samples: comparison/webkit-density-diagnostic.json.
Reproduction: run scripts/installer-landing-motion-diagnostic.mjs with both local
servers running. It writes a fresh .wrangler/pulse-webkit-motion-diagnostic.json.
Disabling grain, blur, masking or promoting layers individually did not restore
normal motion. Temporary diagnostic styles were NOT committed to the product.
Evidence points to the prototype's rendering cost under this WebKit environment,
not an implementation-only failure. It does NOT prove smoothness on real Safari.
Remaining acceptance: real Safari/iPhone/iPad motion review, or a separately
reviewed rendering optimization preserving the supplied visual direction.
